## 1. Descripción del Módulo

### 1.1 Propósito

Definir la arquitectura multi-tenant óptima para el IDP-App Asistente Contable, garantizando aislamiento de datos entre clientes (despachos contables y sus respectivos clientes), escalabilidad horizontal para soportar crecimiento de 10x, y cumplimiento normativo mexicano (SAT, NIF, privacidad de datos).

La arquitectura multi-tenant es crítica para el modelo de outsourcing contable, donde un despacho contable gestiona múltiples clientes finales desde una única plataforma, requiriendo:
- Aislamiento estricto de datos entre tenants (clientes del despacho)
- Configuraciones personalizadas por tenant (catálogo de cuentas, flujos de aprobación)
- Métricas de uso y billing diferenciado por tenant
- Cumplimiento de regulaciones de residencia de datos (México)

### 1.2 Actividades del Contador que Automatiza

| Actividad | Frecuencia | Tiempo Actual | Tiempo Esperado | Ahorro |
|-----------|------------|---------------|-----------------|--------|
| Configuración de nuevo cliente en sistema | Por cliente (5-10/mes) | 2-3 horas | 15 minutos | 90% |
| Aislamiento y segregación de datos por cliente | Diario | 1 hora/día | Automático | 100% |
| Generación de reportes por cliente | Semanal | 4 horas/semana | 30 minutos | 87% |
| Gestión de accesos y permisos por usuario | Por usuario (2-5/mes) | 30 minutos | 5 minutos | 83% |
| Auditoría de accesos cross-tenant | Mensual | 8 horas/mes | Automático | 100% |

### 1.3 Dolor Principal que Resuelve

**Problema central:** Los despachos contables que gestionan 10-100+ clientes enfrentan:

1. **Riesgo de fuga de datos cross-tenant:** Un error de código (WHERE tenant_id faltante) puede exponer datos de todos los clientes simultáneamente
2. **Complejidad operativa:** Mantener instancias separadas por cliente es costoso e insostenible a escala
3. **Inconsistencia en actualizaciones:** Desplegar fixes de seguridad a 50+ instancias toma días, creando ventanas de vulnerabilidad
4. **Costos de infraestructura:** 100 clientes × $500/mes = $50,000/mes vs. $5,000/mes con multi-tenant bien arquitecturado
5. **Imposibilidad de escalar:** Modelos single-tenant no soportán crecimiento de 10x sin refactorización costosa

**Impacto emocional:** Estrés constante por riesgo de brechas de datos, miedo a auditorías fallidas, pérdida de confianza de clientes.

### 3.2 Modelos de Multi-Tenancy

#### Modelo 1: Shared Database, Shared Schema (Pool Model)

**Recomendado para:** 80% de casos (MVP → 10k tenants)

```python
# Tabla con tenant_id obligatorio
CREATE TABLE clientes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,  -- NUNCA nullable
    rfc VARCHAR(13) NOT NULL,
    razon_social VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    -- Índices compuestos (tenant_id primero)
    INDEX idx_tenant_rfc (tenant_id, rfc),
    INDEX idx_tenant_created (tenant_id, created_at)
);

# Query SIEMPRE con tenant_id
SELECT * FROM clientes 
WHERE tenant_id = 'acme-corp-uuid' 
  AND id = 'cliente-123';
```

**Ventajas:**
- ✅ Menor costo operativo (1 DB para todos)
- ✅ Actualizaciones instantáneas (1 schema)
- ✅ Escalabilidad probada (GitHub, HubSpot)

**Desventajas:**
- ❌ Riesgo de brecha si falta WHERE tenant_id
- ❌ Noisy neighbor (un tenant consume recursos)
- ❌ Personalización limitada

#### Modelo 2: Shared Database, Separate Schemas (Bridge Model)

**Recomendado para:** Tenants enterprise que requieren aislamiento

```python
# PostgreSQL: Schema por tenant
CREATE SCHEMA tenant_acme;
CREATE SCHEMA tenant_beta;

# Tablas idénticas en cada schema
CREATE TABLE tenant_acme.polizas (
    id UUID PRIMARY KEY,
    ejercicio INTEGER,
    periodo INTEGER,
    ...
);

CREATE TABLE tenant_beta.polizas (
    id UUID PRIMARY KEY,
    ejercicio INTEGER,
    periodo INTEGER,
    ...
);
```

**Ventajas:**
- ✅ Mejor aislamiento (schema separado)
- ✅ Personalización por tenant (índices, vistas)
- ✅ Menor riesgo de fuga cross-tenant

**Desventajas:**
- ❌ Mantenimiento de schemas (migraciones × N tenants)
- ❌ Analytics cross-tenant complejo

#### Modelo 3: Separate Databases (Silo Model)

**Recomendado para:** Banca, gobierno, healthcare (HIPAA, FedRAMP)

```python
# Base de datos por tenant
tenant_acme_prod_us_east_1
tenant_beta_prod_us_east_1
tenant_gamma_prod_eu_west_1

# Conexión dinámica desde aplicación
def get_db_connection(tenant_id):
    tenant_config = get_tenant_config(tenant_id)
    return psycopg2.connect(
        host=tenant_config['db_host'],
        database=tenant_config['db_name'],
        user=tenant_config['db_user'],
        password=tenant_config['db_password']
    )
```

**Ventajas:**
- ✅ Máximo aislamiento (físico)
- ✅ Cumplimiento normativo simplificado
- ✅ Sin noisy neighbor

**Desventajas:**
- ❌ Costo elevado ($500-1000/mes por tenant)
- ❌ Complejidad operativa (N DBs que mantener)

### 3.3 Implementación de Row-Level Security (RLS)

**Patrón recomendado para IDP-App:** Shared Schema + RLS

```python
# 1. Habilitar RLS en TODAS las tablas
ALTER TABLE clientes ENABLE ROW LEVEL SECURITY;
ALTER TABLE polizas ENABLE ROW LEVEL SECURITY;
ALTER TABLE cfdi ENABLE ROW LEVEL SECURITY;
ALTER TABLE usuarios ENABLE ROW LEVEL SECURITY;

# 2. Crear política de aislamiento (fail-closed)
CREATE POLICY tenant_isolation_polizas ON polizas
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

CREATE POLICY tenant_isolation_clientes ON clientes
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

# 3. Forzar contexto en cada transacción
def execute_with_tenant_context(tenant_id, operation):
    """
    Ejecuta operación con contexto de tenant aislado.
    Garantiza fail-closed: si falla, cero acceso a datos.
    """
    with psycopg2.connect(DSN) as conn:
        with conn.cursor() as cur:
            # SET LOCAL es transaccional (se revierte al commit/rollback)
            cur.execute(
                "SET LOCAL app.current_tenant = %s",
                (str(tenant_id),)
            )
            
            # Ejecuta operación (RLS aplica automáticamente)
            operation(cur)
            
            # Commit revierte SET LOCAL automáticamente
            conn.commit()

# 4. Ejemplo de uso
def get_polizas(tenant_id, ejercicio, periodo):
    def operation(cur):
        cur.execute("""
            SELECT * FROM polizas 
            WHERE ejercicio = %s AND periodo = %s
        """, (ejercicio, periodo))
        return cur.fetchall()
    
    return execute_with_tenant_context(tenant_id, operation)
```

### 3.4 Middleware de Contexto Multi-Tenant

```python
# FastAPI middleware para extraer tenant_id del JWT
from fastapi import Request, HTTPException
from jose import jwt

async def multi_tenant_middleware(request: Request, call_next):
    """
    Extrae tenant_id del JWT y establece contexto para toda la request.
    """
    # 1. Obtener token de Authorization header
    auth_header = request.headers.get('Authorization')
    if not auth_header or not auth_header.startswith('Bearer '):
        raise HTTPException(status_code=401, detail="Token requerido")
    
    token = auth_header.replace('Bearer ', '')
    
    # 2. Validar y decodificar JWT
    try:
        payload = jwt.decode(
            token,
            SECRET_KEY,
            algorithms=['HS256'],
            options={'verify_exp': True}
        )
        tenant_id = payload.get('tenant_id')
        user_id = payload.get('user_id')
        role = payload.get('role')
        
        if not tenant_id:
            raise HTTPException(status_code=403, detail="tenant_id requerido")
    except jwt.JWTError:
        raise HTTPException(status_code=401, detail="Token inválido")
    
    # 3. Inyectar contexto en request state
    request.state.tenant_id = tenant_id
    request.state.user_id = user_id
    request.state.role = role
    
    # 4. Continuar con request
    response = await call_next(request)
    return response

# 5. Uso en endpoints
@app.get('/v1/polizas')
async def get_polizas(request: Request, ejercicio: int, periodo: int):
    tenant_id = request.state.tenant_id  # Contexto disponible
    
    # Query usa tenant_id automáticamente (RLS)
    polizas = db.execute(
        "SELECT * FROM polizas WHERE ejercicio = %s AND periodo = %s",
        (ejercicio, periodo)
    )
    
    return {'polizas': polizas}
```

## 4. Limitantes y Restricciones

### 4.1 Limitación 1: Noisy Neighbor

**Problema:**
Un tenant con alto volumen de operaciones (ej. 10k CFDI/día) puede consumir recursos de CPU/memoria, degradando rendimiento para otros tenants en la misma infraestructura compartida.

**Solución:**
```python
# Kubernetes: Resource Quotas por tenant
apiVersion: v1
kind: ResourceQuota
metadata:
  name: tenant-acme-quota
  namespace: tenant-acme
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 4Gi
    limits.cpu: "4"
    limits.memory: 8Gi
    pods: "50"

# PostgreSQL: Limitar queries costosas
ALTER ROLE tenant_acme_user SET statement_timeout = '30s';
ALTER ROLE tenant_acme_user SET max_connections = 20;
```

**Impacto:**
- Costo adicional de monitoreo (Prometheus + Grafana)
- Complejidad de configuración inicial
- Requiere tuning continuo según crecimiento

### 4.2 Limitación 2: Migraciones de Schema Complejas

**Problema:**
Con 100+ tenants, aplicar migraciones de schema (ej. agregar columna) requiere coordinación para evitar downtime y garantizar consistencia.

**Solución:**
```python
# Estrategia: Migraciones en background con feature flags
def migrate_tenant_schema(tenant_id, migration_version):
    """
    Aplica migración a tenant específico sin downtime.
    """
    # 1. Marcar tenant como "en migración"
    db.execute(
        "UPDATE tenants SET migration_status = 'in_progress' WHERE id = %s",
        (tenant_id,)
    )
    
    # 2. Aplicar migración (idempotente)
    run_migration(migration_version, tenant_id)
    
    # 3. Validar migración
    if validate_migration(tenant_id, migration_version):
        db.execute(
            "UPDATE tenants SET migration_status = 'completed' WHERE id = %s",
            (tenant_id,)
        )
    else:
        # Rollback automático
        rollback_migration(tenant_id, migration_version)
        db.execute(
            "UPDATE tenants SET migration_status = 'failed' WHERE id = %s",
            (tenant_id,)
        )

# Feature flag para activar nueva funcionalidad por tenant
def is_feature_enabled(tenant_id, feature_name):
    enabled_tenants = get_feature_flags(feature_name)
    return tenant_id in enabled_tenants
```

**Impacto:**
- Complejidad de testing (N tenants × M versiones)
- Requiere rollback automático
- Ventana de migración: 5-10 minutos por tenant

## 8. Conclusiones y Recomendaciones

### 8.1 Hallazgos Clave

1. **Shared Schema + RLS es el modelo óptimo** para 80% de casos: balancea costo, complejidad y seguridad
2. **tenant_id debe ser primera columna en índices compuestos** para optimizar queries
3. **RLS fail-closed es no negociable:** cada falla debe resultar en cero acceso, nunca acceso cross-tenant
4. **Testing de aislamiento debe ser automatizado y diario:** una brecha = quiebra potencial
5. **Kubernetes resource quotas previenen noisy neighbor:** esencial para SLA de 99.9%

### 8.2 Recomendaciones Finales

| Área | Recomendación | Prioridad | Owner |
|------|---------------|-----------|-------|
| **Arquitectura** | Iniciar con Shared Schema + RLS | ALTA | Arquitecto SaaS |
